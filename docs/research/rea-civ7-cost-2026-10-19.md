# 用 REA 尽可能还原《文明 VII》：能力与成本证据

调研日期：2026-10-19（Asia/Shanghai）。目标按用户确认的“尽可能还原整个游戏”理解。完成了官方项目与一手文档调研，以及本机游戏文件、Mach-O 元数据的只读清点；没有安装 REA、启动游戏、反编译程序或修改工具配置。在线仓库正在快速更新，下述数量均为查阅时快照。

## 核心判断

REA 可以把反编译器、程序文件和运行观察接入 AI 编程代理，帮助逐函数理解、重新实现和验证。它没有提供“输入大型商业游戏，直接得到完整原工程”的已验证产品能力。对《文明 VII》这样的目标，应把费用理解为长期重建工程：工具许可、模型用量、实验和验收工作量；不能把一次反编译导出的伪代码当作完成品，也不能用安装包 GB 数乘一个单价。

这是基于下面公开证据的工程判断。此次未找到可复核的“REA 完整还原现代 AAA 游戏”案例，也没有找到对应的完整账单、总 token 或人时基准。这里的“未找到”限定于查阅的官方 README、官网案例、官方实验目录、所链接重建仓库和相关仓库搜索，不是证明所有私人项目都不存在。

**预算建议：先给个人试点设 ¥1,000–3,000、1–2 周的上限，验证一个完整机制。完整重建目前不能给可信的封顶总价。** 下文的模型用量情景会产生约 ¥2.8 万–56 万的大规模 API 支出；如设定 3–5 人、1–3 年的团队投入，人力成本情景为 ¥72 万–720 万。这些是透明假设下的预算压力测试，不是实测的 Civ7 还原报价、所需最低投入或交付工期预测；花完预算也可能只完成部分系统。

## REA 实际提供什么

- REA 作者代码为 MIT 许可；原生分析调用独立安装的 Ghidra、Hopper 或 IDA。它提供伪代码、汇编、字符串、符号、调用和引用信息，代理再据此写实现并测试。JavaScript/Electron 静态分析不需要原生反编译器。[官方 README](https://github.com/morluto/rea#how-rea-works)
- 分析工作在本地进行，结果会交给所使用的代理和模型服务商。因此“本地分析”不等于“没有模型费用”，也不等于模型从未接收分析结果。[官方 FAQ](https://github.com/morluto/rea#faq)
- 当前主分支要求 Node.js 22.x ≥22.19、24.x ≥24.11 或 26+；安装方式支持 Codex 等 MCP 客户端。主分支文档与 npm 已发布版本可能不同，应记录实际版本和工具清单。[官方安装文档](https://github.com/morluto/rea/blob/main/docs/installation.md)

**对整游戏还原的含义（推断）：**需要另外完成类型与状态重建、跨模块关系、构建工程、图形和音频接口、资源格式、输入/存档/随机数/AI 规则、多人同步以及大量行为对照。编译后的文件通常不足以唯一确定原作者的源码写法、注释、变量名、项目结构和开发工具；可以追求行为接近或可维护的重实现，不能预先承诺找回原工程。仅有客户端材料，也不能据此承诺恢复未包含的服务端实现。

## 公开游戏案例：进展很实在，但要读验收范围

### DX-Ball 1.07：数百函数，不是现代 AAA

REA 官网案例停留在 **2026-10-07**：55 个维护函数、33 个编译字节匹配函数；单个声像函数通过 3,205 个原版 x86 对照并匹配 63 字节。该旧页面仍写可玩游戏在开发，不能拿它描述仓库的最新进度。[官网案例](https://rea.tools/showcase/dx-ball/)

实时仓库进度账本已达到：553 个候选、475 个有源码、249 个有范围明确的语义验收、395 个完整字节匹配函数，共 85,106 字节。候选库存还包括运行库和编译器生成代码，不能把全部数量都称作游戏业务函数。[当前进度账本](https://github.com/N0zoM1z0/dx-ball/blob/main/docs/PROGRESS.md)

账本提到两个 Windows 构建曾在 Wine 完成所记录的原版关卡 campaign，但更细的 **2026-10-17 当前 restored-CRT 镜像**记录为：14,400 秒观察截止，停在第 20 关，观察器返回失败，明确不构成完整 50 关验收，也不证明游戏崩溃。历史版本的完成记录不能自动转移到当前版本。[当前原版关卡验收记录](https://github.com/N0zoM1z0/dx-ball/blob/main/docs/research/ORIGINAL_CAMPAIGN.md)

这证明 REA + Codex + Ghidra 的逐函数恢复与编译对照工作流有成果；同时说明从“有源码/字节相同”到“整款正确运行”还有独立验证成本。[项目工作流](https://github.com/N0zoM1z0/dx-ball#reconstruction-with-rea)

### TH04：很高的函数精确率，也不等于完整游戏验收

当前账本为四个产品合计 663 个作者函数候选、661 个精确函数、2 个阻塞项。MAIN 的 99.97% 是已审查作者 C/C++ 范围中的字节比例，不是整个 EXE 或全部游戏的完成百分比。[当前进度](https://github.com/N0zoM1z0/th04/blob/main/docs/PROGRESS.md)

README 明确保留“完整游戏与原版时序验收未完成”，后续仍有全流程、连续显示与物理时序等边界。原版 MAIN.EXE 只有 156,258 字节，是 16 位 PC-98 DOS 游戏。[当前 README](https://github.com/N0zoM1z0/th04)

REA 官网本次展示的是弹幕角度函数和 2,139 字节的生成代码对照；页面也明确早期重建使用项目自身分析脚本，此次添加了新的 REA 检查。不能把整个 TH04 仓库的历史工作量和成果全部归功于 REA，更不能由此推出大型现代游戏可以同价完成。[TH04 官方案例](https://rea.tools/showcase/th04/)

## 公开 token、时间和费用基准

找到了真实代理用量实验，但**没有找到上述游戏重建的累计美元账单、累计 token 或累计人工工时**。官方实验主要回答某个局部问题，不是从零完成可玩游戏。

REA 的原生入口实验记录如下，使用 Codex CLI 0.161.0、请求模型别名 `gpt-5.6-terra`、high reasoning、七个指定工具；实际服务端模型身份未进一步确认：

| 任务 | 总输入 token | 其中缓存输入 | 非缓存输入 | 输出 token | 墙钟时间 | 调用数 / 失败数 |
|---|---:|---:|---:|---:|---:|---:|
| PE 入口 1 | 451,337 | 399,616 | 51,721 | 3,820 | 130.073 秒 | 12 / 2 |
| DOS 入口 1 | 730,578 | 658,944 | 71,634 | 3,310 | 134.435 秒 | 9 / 0 |
| PE 入口 2 | 498,322 | 429,056 | 69,266 | 3,038 | 192.373 秒 | 9 / 1 |

三次任务验证的是目标身份、入口/函数分类、签名、局部变量、函数范围、伪代码前缀、关系数量等选定事实。不是三个复杂游戏子系统的完整还原，不能将“几分钟”解释成函数重建通用耗时。[完整实验与限制](https://github.com/morluto/rea/blob/main/experiments/analysis-efficiency/native-entry-views.md)

另一个请求 `gpt-6.1-sol/high` 的实验，对**已保留的原生分析证据**进行问答，两组各两次成功任务耗费约 28.7 万–34.9 万总输入 token、52–62 秒；这些不是重新分析完整二进制的成本。[证据复用实验](https://github.com/morluto/rea/blob/main/experiments/analysis-efficiency/retained-investigation-workflows.md)

官方还测得，缩小工具 JSON 回复并不稳定降低真实模型 token 或总耗时，工具发现、重复调用、失败与修正都可能占比很大。[客户端与模型用量实验](https://github.com/morluto/rea/blob/main/experiments/analysis-efficiency/model-context.md)

**计费方法（建议）：**把非缓存输入、缓存输入和输出分别乘对应模型单价，然后累加失败/重试/续接；不要把所有输入都按原价计算，也不要把缓存输入当免费。订阅额度不能直接等同无限 API 用量。对《文明 VII》的有效估算需要先测一个范围明确的样本，记录真正验收通过的成果，而不是仅记录生成代码行数。

## 预算前必须明确的验收口径

以下是工程建议，而非 REA 官方保证：

1. **资料与机制复原**：整理已有脚本、数据表、规则关系及可验证公式；输出文档和测试，不要求独立可玩。
2. **完整单机玩法重实现**：从新局到结束，城市/经济/战斗/外交/AI/地图/存档等关键流程可运行，选择代表性存档和固定随机种子对照原版。
3. **接近完整产品**：进一步要求图形/音频/资源管线、UI、性能、各平台、多人同步、DLC 和所有边界行为。
4. **原版级精确或原工程恢复**：字节精确、时序/随机数精确或希望找回原工程；难度和不确定性进一步上升，不能保证完成。

用户的“尽可能还原整个游戏”适合设为长期方向，但预算需要在第 2 与第 3 层确定实际边界。第 1 层的低成本成功不是第 3 层可廉价完成的证据。建议先用一套可复用的“证据→实现→对照验收”样本测出成本和失败率，再决定投入规模。

## 模型费用：可复算的情景，而非整游戏报价

以下以 2026-10-19 查到的 Claude 官方 API 单价作**计费示例**，不是要求更换现有代理或保证这些模型的还原能力。REA 自身不按游戏大小收费，模型选择和付费渠道是独立事项。

单位均为美元 / 百万 token（MTok）：

| 模型 | 普通输入 | 5 分钟缓存写入 | 缓存命中读取 | 输出 |
|---|---:|---:|---:|---:|
| Sonnet 5.5 | 2 | 2.5 | 0.1 | 10 |
| Opus 5.5 | 4 | 5 | 0.2 | 20 |

来源：[官方 API 价目表](https://platform.claude.com/docs/en/about-claude/pricing)。这是标准速度/默认路由价格，不含税、服务器工具费或其他附加计费。普通输入与缓存写入是不同类别，同一 token 不重复计两次。较长有效期的缓存写入单价更高，失效后重建也会产生费用。

用于直观预算的公式为：`费用 = 普通输入量 × 单价 + 缓存写入量 × 单价 + 缓存读取量 × 单价 + 输出量 × 单价`。所有用量是各轮请求累计计费量，含重复上下文、重试与检查，并非唯一源码长度。下面假设所有新增输入都按 5 分钟缓存写入计费、缓存命中量为新增输入的五倍，普通未缓存输入量为零；不是对真实缓存命中率的预测。

| 假设累计新增输入 / 缓存输入 / 输出 | Sonnet 5.5 | Opus 5.5 | 人民币预算示意 |
|---|---:|---:|---:|
| 1,000 万 / 5,000 万 / 100 万 token | US$40 | US$80 | ¥280–560 |
| 1 亿 / 5 亿 / 1,000 万 token | US$400 | US$800 | ¥2,800–5,600 |
| 10 亿 / 50 亿 / 1 亿 token | US$4,000 | US$8,000 | ¥2.8 万–5.6 万 |
| 100 亿 / 500 亿 / 10 亿 token | US$40,000 | US$80,000 | ¥28 万–56 万 |

人民币仅使用 **US$1 = ¥7 的预算假设**，不是实时汇率报价。任务可能比这些情景更省或更贵；没有证据表明其中任一档用量足以完成 Civ7。低价模型可能需要更多纠错轮次，不能只比较每 token 单价。此表也没有把别的模型的实测 token 当成 Claude 的实测账单。

订阅可以改变个人现金支出：例如 Claude Pro 官方月付 US$20，Max 从 US$100/月起，均存在用量限制；它们不能当成无限 API 或全天候并行重建的承诺。已有代理订阅可先利用可用额度，无须仅为 REA 新开订阅。[官方订阅价格](https://claude.com/pricing)

## 人力、机器与试点预算

**个人学习起步建议（主观预算）：**先用已有 32 GiB Mac、REA + Ghidra，把额外现金上限设为 ¥1,000–3,000，日历时间 1–2 周，主动投入约 20–60 小时。范围只承诺尝试一个有输入输出、能独立对照的机制，不能承诺两周内必定还原成功。无需预先购买 GPU；模型在 API 侧运行，本地主要承担反编译、索引、构建和游戏测试。当前机器是否能顺利处理整个主程序仍需实测，应先串行试验，再决定内存、磁盘或远程机器是否必要。Hopper 的 US$99 为可选额外许可费；Ghidra 路线可保持零工具许可费。

**完整重建的人力压力测试：**如果人为设定 3–5 人、投入 1–3 年，每人每月综合成本 ¥2 万–4 万，则低端为 `3 × 12 × 2万 = 72万元`，高端为 `5 × 36 × 4万 = 720万元`。这些单价是预算参数，不是已调查的薪资行情；人数/时间也不是保证能完成的资源下限。模型费用、额外机器、资源重制和商业工具许可另计。自己承担全部工作可以不支付这笔人工现金，但工作量和时间成本仍在。

完整还原最难预估的部分是跨系统集成、长期对局差异、AI 决策与随机数、存档兼容、图形资源和多人同步。一个可运行的相似实现、可加载原版存档的实现、原版行为精确匹配，验收成本完全不同。单靠增加模型调用量不能保证解决所有缺失信息。

建议试点选一条能穿过“公开 JS → 引擎接口 → 原生逻辑”的局部机制，例如某个单位行动合法性判定或一段产出修正。交付物应是证据地址、类型/规则解释、独立实现和原版对照测试；记录缓存/非缓存/输出 token、机器时间、人工时间、通过率与未解问题。接着再取简单、中等、复杂三类样本估计每个**验收通过的机制**的成本，才有依据决定完整项目下一阶段的预算。
